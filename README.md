# pao-project-quickstart

> 让 AI Agent 带你快速上手一个陌生代码仓库：三步系统分析 + 双图可视化，产出一份可直接照着读的中文入门指南。

接手新项目时最常见的困境是：README 只讲怎么跑起来，不讲代码为什么这样组织；逐文件翻源码耗时且抓不住主干；问 AI 得到的又是零散片段。这个 Agent Skill 把「项目上手」固化成一套可复用的调查流程，一次运行产出一份结构化报告——从技术栈、请求链路，到每个核心模块的设计缘由，再到改代码前必须知道的维护规则。

## 它做什么

运行后，Agent 会对目标仓库执行三步分析，并生成 `项目入门指南-<项目名>-<YYYYMMDD>.md`：

| 步骤 | 内容 | 回答的问题 |
| --- | --- | --- |
| **1. 整体架构** | 语言与技术栈、核心依赖、构建命令表、目录树与进程入口、**请求路径时序图** | 这是什么项目？怎么跑起来？一条请求怎么流转？ |
| **2. 核心模块剖析** | **分层颜色分块架构图** + 逐模块的设计缘由（Why）/ 设计原则 / 设计模式 / 文件分布 | 代码为什么这样组织？每个模块解决什么问题？ |
| **3. 维护方式** | 协作流程、CI/CD、测试与评测门禁、代码质量、发布流程、文档制度、监控运维 | 改代码要遵守什么规则？怎么安全地提交？ |

报告末尾附 3–5 条带 `file:line` 的下一步学习路径（如「从入口 X 的 Y 函数 trace 一条典型请求」），可以直接照着走读。

## 核心设计

### 双图可视化，配色跨图一致

报告包含两张 Mermaid 图，同一架构层在两图中颜色相同，可互相对照：

- **§1.6 请求路径时序图**（`sequenceDiagram`）：用 `box rgb(...)` 按层给参与者分组着色，`loop`/`alt`/`opt` 表达核心循环、分支与可选流程，一条 `note` 概括断线恢复等异常语义
- **§2.0 整体架构图**（`flowchart`）：按架构层分 subgraph，`classDef` 统一配色（浅色填充 + 同系描边）；箭头体现依赖方向，虚线表示「端口由外层实现」；每个节点标注对应剖析小节编号，可按图索骥

统一配色：蓝＝前端、青＝呈现层、绿＝应用层、黄＝领域层、紫＝基础设施、红＝装配根、灰＝进程外依赖。

### 领域层展开到子模块

架构图中的领域层/核心层不允许压成一个笼统大节点，必须展开为与实际目录一一对应的子模块（DDD 项目按子域逐个画），连线也细化到子模块——这是读懂业务代码组织方式的关键。

### 图只导航，细节进正文

硬性精炼约束，防止图膨胀到不可读：

| 约束 | 上限 |
| --- | --- |
| 时序图参与者 | ≤7（同层职责相近的合并） |
| 时序图消息 | ≤25 条 |
| 架构图节点文案 | 每个 1 行 |
| 读图要点 | 4–6 条，每条一两句 |

超时秒数、加密算法等参数级细节一律不画进图，写进对应正文小节。

### 证据优先，不编造

- 设计缘由必须有源码/注释/ADR/commit message 佐证，给到文件位置；不确定的明确标「推测」
- 维护方式逐项调查，无证据的写「未发现」
- README 声明的「已验证 vs 待验收」边界如实转述，不夸大
- 模块超过 12 个时按最近 3 个月修改频次取 Top 8–10，并明确告知裁剪规则
- `AGENTS.md` / `CLAUDE.md` 等 AI 协作约定文件优先读取——它们常包含交付门禁，直接影响「维护方式」结论

### 交付前自检

生成报告前自动核对：根目录关键配置无遗漏、双图配色一致、精炼约束达标、Mermaid 语法可渲染。

## 安装

clone 到你的 Agent 技能目录（目录名须与 SKILL.md 中 `name` 一致）：

```bash
# QwenWork
git clone https://github.com/pao-coder66/pao-project-quickstart.git ~/.qwenworkcn/skills/pao-project-quickstart

# Claude Code
git clone https://github.com/pao-coder66/pao-project-quickstart.git ~/.claude/skills/pao-project-quickstart
```

新会话生效。纯 prompt 驱动，无脚本、无额外依赖，任何支持 Agent Skills 的宿主均可使用。

## 使用

对 Agent 说：

```
快速上手这个项目 /path/to/repo
带我熟悉这个仓库
分析这个项目
```

也可以只要某一步：「只分析这个项目的核心模块」。

**运行要求**：Agent 需能读取目标仓库并执行 shell（用于目录侦察、`git log` 统计）；超大项目（>100k LOC）建议宿主支持子代理并行调查。

**查看报告**：任何支持 Mermaid 的 Markdown 渲染器（GitHub、Typora、VS Code + Mermaid 插件）。注意时序图的 `box rgb(...)` 分组着色需 **Mermaid ≥10.3**。

## 产出示例（报告结构）

```
项目入门指南-<项目名>-<YYYYMMDD>.md
├── 一、项目整体架构
│   ├── 1.1–1.5 技术栈 / 依赖 / 背景 / 构建命令 / 目录与入口
│   └── 1.6 请求路径总览（文字链路 + 多颜色时序图）
├── 二、核心模块逐一剖析
│   ├── 2.0 整体架构视角（颜色分块架构图 + 读图要点 + 过渡）
│   └── 2.1–2.N 各模块：Why / 原则 / 模式（含代码位置）/ 关键文件
├── 三、项目维护方式
│   └── 协作 / CI / 测试与门禁 / 质量 / 发布 / 文档 / 运维
└── 下一步建议（3–5 条带 file:line 的学习路径）
```

## 定制

整个 skill 就是一份 `SKILL.md`，可直接修改：

- **配色表**：§2.0 的「统一配色表」集中定义两张图的颜色
- **精炼阈值**：参与者/消息/要点数量上限写在 §1.6、§2.0 与「注意事项」
- **裁剪规则**：模块数量阈值与频次统计命令在 §2.1
- **报告命名与结构**：「验证与最终交付」一节
